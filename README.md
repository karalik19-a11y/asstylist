# asStylist

**AI fashion director в Telegram Mini App.** По фотографии, росту, весу, выбранному стилю,
настроению и бюджету до **100 000 ₽** собирает персональный fashion look из проверенных товаров —
и объясняет, почему выбрана каждая вещь.

Сервис некоммерческий. Стоимость для пользователя — **0 ₽**: стек полностью бесплатный,
анализ фото по умолчанию работает локально, без API-ключей и внешних вызовов.

---

## Быстрый старт (2 команды)

```bash
make setup     # python venv + npm install
make run       # сборка Mini App + API на http://localhost:8000
```

Откройте `http://localhost:8000` — приложение работает и в обычном браузере (демо-режим),
и внутри Telegram как Mini App.

Без Makefile:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
npm --prefix frontend install
npm --prefix frontend run build
.venv/bin/python -m uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

Docker:

```bash
docker compose up --build     # http://localhost:8000
```

## Архитектура

```
Telegram Mini App (React + TS + Vite)
        │  fetch /api/*  (один origin, без CORS-боли)
        ▼
FastAPI  ──►  Fashion Engine (поиск + подбор)  ──►  Budget Optimiser  ──►  Look
   │                    ▲                            ▲
   │                    │ каталог как провайдер      │ Fashion Ranking Engine
   │                    │                            │ (страховка бюджета и слотов)
   │                    │ только eligible-товары
   ├──► Verification Layer (schema / price / url / source / checksum / TTL)
   ├──► Vision (локальный Pillow-анализ, опционально OpenAI/Gemini)
   └──► SQLite (SQLAlchemy) — пользователи, образы, каталог
```

**Стек и почему он такой:**

| Слой | Технология | Причина |
| --- | --- | --- |
| Frontend | React 18 + TypeScript + Vite | самый стабильный и лёгкий вариант под Telegram WebView |
| Backend | FastAPI + Pydantic v2 | быстрый, типизированный, авто-доки на `/docs` |
| БД | SQLite через SQLAlchemy | 0 ₽, ноль настройки, один файл; замена на Postgres = одна строка `DATABASE_URL` |
| Vision | Pillow | офлайн, без моделей и ключей; опциональный апгрейд до GPT-4o-mini / Gemini |
| Тесты | pytest + vitest/RTL | покрывают и движок, и HTTP, и UI |
| Хостинг | один процесс, один порт | Mini App требует HTTPS-статики — её отдаёт тот же FastAPI |

## Как считает Fashion Ranking Engine

Этот ранжировщик остаётся в приложении как страховка: движок отвечает за вкус и архитектуру
образа (см. [Fashion Engine](#fashion-engine--поиск-и-подбор-вещей)), а восемь факторов ниже
удерживают бюджет, размеры, сезонность и верификацию товара.

Каждый товар получает оценку 0…1 как взвешенную сумму восьми факторов:

| Фактор | Вес | Что измеряет |
| --- | --- | --- |
| `style` | 0.28 | попадание в выбранный стиль (точное / соседнее / чужое) |
| `silhouette` | 0.16 | совместимость кроя с силуэтом (рост + вес + фото) |
| `mood` | 0.15 | совпадение с настроением |
| `color` | 0.15 | гармония цвета с палитрой пользователя и его любимыми цветами |
| `formality` | 0.08 | соответствие поводу (работа, свидание, событие…) |
| `value` | 0.08 | рейтинг, число отзывов, честность цены к медиане категории |
| `season` | 0.05 | сезонность, включая соседние сезоны |
| `verification` | 0.05 | насколько товар проверен |

Веса настраиваются через `RANKING_WEIGHTS_JSON` без изменения кода и всегда нормализуются к 1.

Дальше:

1. **Жёсткие фильтры** — товар не рассматривается, если он дороже бюджета, не прошёл
   верификацию, состоит только из нелюбимых цветов, не имеет нужного размера или не подходит
   по посадке. Причины попадают в `diagnostics.rejected_sample`.
2. **План образа** — многослойный, лёгкий или «на основе платья» (зависит от сезона, повода и
   бюджета: при бюджете < 15 000 ₽ верхняя одежда убирается первой).
3. **Бюджетный оптимизатор** — сначала распределяет бюджет по слотам, затем «ремонтирует» образ
   вниз (самые дешёвые потери качества на рубль), затем докупает апгрейды с лучшей отдачей на
   рубль. Необязательные слоты (сумка, аксессуар) могут быть убраны. Алгоритм детерминированный:
   одинаковый вход → одинаковый образ.
4. **Цельность образа** — отдельно считается согласованность цвета, стиля и формальности; итоговые
   0…100 = 62 % средняя оценка вещей + 38 % цельность. Отсюда же вердикт A/B/C/D.
5. **Объяснения** — для каждой вещи генерируются причины на русском, а не «AI так решил».

## Fashion Engine — поиск и подбор вещей

Подбор вещей и свободный поиск выполняет движок **ASSTYLIST Fashion Engine** из
[github.com/karalik19-a11y/-](https://github.com/karalik19-a11y/-). Он портирован на Python
(`backend/app/fashion_engine/`, ~28 модулей) и работает полностью офлайн: ни сети, ни ключей,
ни внешних сервисов. Порт сохраняет поведение оригинала и добавляет русские основы в таблицы
ключевых слов, чтобы запросы на русском («грязный индустриальный образ с прозрачным верхом»)
расширялись так же, как английские.

```
запрос пользователя
   → Query Expander (до 14 расширенных запросов)
   → провайдеры поиска (каталог asStylist + mock-архетипы дизайнеров + живой web-поиск)
   → Fashion Intelligence: материалы, силуэты, палитра, тренды
   → Taste Engine + anti-generic отсев (нишевость 0…100, рейтинг fashion score 0…100)
   → Item Validator (confidence, бренд, ссылка на источник) → Image Matcher
   → Product Identity Resolver (дедуп brand::name)
   → Outfit Architect: роли hero / base / layer / footwear / accessory, ≥ 3 вещей
   → Outfit Scorer (0…100) → Fashion Critic (APPROVE / REVISE / REBUILD)
   → стилистический тезис + логика образа + альтернативы
```

**Живой web-поиск вещей.** `WebSearchProvider` дополняет выдачу находками из интернета в
реальном времени — каждая приходит с названием, ценой, ссылкой **и фото товара прямо с
источника** (UI показывает фото живьём, без локального хранения). Источники включаются независимо
и работают одновременно, сортируясь по релевантности запросу:

- `SERPAPI_API_KEY` — Google Shopping через SerpAPI (бесплатный тариф — 100 запросов/мес);
- `GOOGLE_CSE_API_KEY` + `GOOGLE_CSE_CX` — Google Custom Search по запросам вида «купить …»;
- `PRODUCT_FEED_URL` — партнёрский фид магазина (JSON-массив позиций) как первичный источник.

Цены нормализуются в рубли курсами `FX_RATES` (для CSE/фида) или берутся из
`extracted_price` SerpAPI. Мастер-выключатель — `WEB_SEARCH_ENABLED=false`. Mock-провайдер
дизайнерских архетипов (`FASHION_ENGINE_ENABLE_MOCK=true`, включён по умолчанию) даёт нишевый
референс-ряд и ведёт на живой поиск ритейлера.

**Как это сочетается с Fashion Ranking Engine приложения.** Движок отвечает за вкус и
архитектуру образа, приложение — за бюджет, размеры и верификацию:

| Режим | `FASHION_ENGINE_MODE` | Поведение |
| --- | --- | --- |
| Гибридный (по умолчанию) | `hybrid` | движок собирает образ, бюджетный оптимизатор и слоты приложения доводят его до лимита |
| Только движок | `engine` | образ и оценка целиком от движка |
| Прежний ранжировщик | `legacy` | Fashion Ranking Engine без движка |

Позиция вещи в гибридном режиме: `0.55 * оценка движка + 0.30 * оценка приложения + 0.15 * ранг в
шортлисте`, итоговая оценка образа: `0.7 * приложение + 0.3 * движок`. Если движок не собрал образ
(например, каталог пуст), `FASHION_ENGINE_ALLOW_FALLBACK=true` возвращает прежний ранжировщик — в
`diagnostics.engine.pipeline` будет `legacy-ranker`.

**Что видно в интерфейсе:** экран «Поиск по движку» отдаёт тезис образа, оценку, вердикт критика,
состав по категориям вкуса и подобранные вещи; в карточке образа — блок `ТЕЗИС ДВИЖКА`, а у каждой
вещи — роль, категория вкуса и fashion score.

**Эндпоинты движка** (полная схема — `/docs`):

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/engine/health` | версия, пайплайн, размер каталога |
| `GET` | `/api/engine/schema` | tool-схема движка (`asystylist_create_outfit`) |
| `GET` | `/api/engine/taxonomy` | стили-профили, тезисы, категории вкуса, роли |
| `POST` | `/api/engine/search` | свободный поиск вещей по запросу (тезис + вещи + подсказка для генерации) |
| `POST` | `/api/engine/outfit` | прямой прогон движка (camelCase API, паритет с оригиналом) |

```bash
curl -s -X POST localhost:8000/api/engine/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"грязный индустриальный образ с прозрачным верхом","style":"grunge","niche_level":82}' \
  | jq '{thesis:.engine.styling_thesis_ru, items:[.items[].name]}'
```

## Product verification layer

Каждая карточка товара проходит 9 проверок; критическая ошибка означает, что товар **не попадёт
в образ вообще**:

| Проверка | Вес | Критическая |
| --- | --- | --- |
| `schema` — обязательные поля | 0.18 | да |
| `price` — вменяемая цена в ₽ (≤ 100 000) | 0.15 | да |
| `url` — https + хост из белого списка (защита от SSRF) | 0.20 | да |
| `category` — категория известна движку | 0.10 | да |
| `source` — доверенный источник | 0.08 | да |
| `checksum` — карточка не изменена после верификации | 0.04 | да |
| `attributes` — цвета/стили/сезоны заполнены | 0.12 | нет |
| `sizes` — указаны размеры | 0.10 | нет |
| `freshness` — TTL верификации (30 дней) | 0.03 | нет |
| `reachability` — живой HTTP-запрос | 0.05 | нет, по умолчанию **выключено** |

Статусы: `verified` (≥ 0.92 и без критических ошибок), `warning` (≥ 0.6), `failed`.
Отчёт доступен в приложении («Проверка товаров») и в `GET /api/catalog/verification`.

В демо-каталоге намеренно лежат 4 битые карточки (`BAD-001…BAD-004`): ссылка на чужой хост,
нулевая цена, отсутствие атрибутов, неизвестная категория. Все четыре отклоняются.

## Подключение к Telegram — 3 шага

Приложение полностью готово к Telegram: проверка подписи `initData`, тема оформления,
HapticFeedback, открытие ссылок внутри Telegram — всё уже работает. Не хватает только вашего бота,
которого создаёт @BotFather (это нельзя сделать без вас).

**1.** Выложите приложение на любой публичный HTTPS-адрес (Telegram не принимает localhost).
Бесплатные варианты: Render, Railway, Fly.io, VPS + Caddy.

```bash
make run          # или: docker compose up --build
```

**2.** В [@BotFather](https://t.me/BotFather) → `/newbot` → скопируйте токен.

**3.** Подключите бота — любым из двух способов:

*В интерфейсе:* откройте приложение в браузере → карточка «Подключить своего Telegram-бота» →
вставьте токен и адрес → «Подключить». Бэкенд сам проверит токен, повесит Mini App на кнопку меню
бота и пропишет команды `/start`, `/looks`, `/help`. Токен сохранится в `.env` (файл в .gitignore),
перезапуск не нужен.

*В терминале:*

```bash
make connect-tg BOT_TOKEN=123456:ABC-DEF WEB_APP_URL=https://your-domain.example
# добавить --strict, чтобы отключить демо-доступ из браузера
```

Готово: откройте `https://t.me/ваш_бот` — кнопка слева от поля ввода запускает asStylist.

Проверить подключение: `GET /api/telegram/status` (возвращает имя бота, но никогда сам токен).

### Режимы работы

**Демо / локальный** (`DEMO_MODE=true`, по умолчанию) — не нужен ни токен бота, ни сеть, ни
ключи AI. Фото анализируется Pillow, каталог сидируется из репозитория, пользователи создаются
как локальные демо-идентичности. Идеально для разработки и ревью.

**Telegram** — после шагов выше. Подпись `initData` проверяется по стандартному алгоритму
HMAC-SHA256 (`backend/app/telegram/auth.py`); просроченные и подделанные данные отклоняются.
Пока `DEMO_MODE=true`, браузерный доступ сохраняется рядом с настоящей Telegram-авторизацией —
удобно для отладки; `--strict` его выключает.

**AI-провайдер** — `AI_PROVIDER=local|openai|gemini`. Если удалённый вызов не удался, приложение
молча возвращается к локальному анализу: образ соберётся в любом случае.

## Приватность

Фото по умолчанию **не сохраняется**: из него извлекаются признаки (доминирующие оттенки,
подтон, пропорции), а байты отбрасываются. В образе остаётся только SHA-256-отпечаток — чтобы
повторная генерация была воспроизводимой. `STORE_PHOTOS=true` включает сохранение, если оно
вам действительно нужно.
